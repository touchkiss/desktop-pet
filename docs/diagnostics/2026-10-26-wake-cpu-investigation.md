## 源码检查

- `Sources/DesktopPet/ClipMedia.swift:38`：每个 AlphaVideoPlayback 长期持有同一个 AVPlayer。
- `Sources/DesktopPet/ClipMedia.swift:94`：切换片段时替换 AVPlayerItem，并为每个 item 挂载 BGRA AVPlayerItemVideoOutput；普通播放也一直挂着供快照使用的输出。
- `Sources/DesktopPet/ClipMedia.swift:156`：stop 清空 item，但没有重建 AVPlayer 或 AVPlayerLayer。
- 在 Sources 中未发现 NSWorkspace 系统睡眠、唤醒、显示器睡眠和唤醒通知处理。不能据此认为系统睡眠时 CPU 仍在运行；缺的是应用对睡眠前后状态的主动管理。
- PlaylistEngine.restartTimer 会先 invalidate 旧 timer，且有 timerRevision 防过期回调；没有找到重复创建未清理播放 timer 的证据。
- 当前库启用了 60 秒空闲放大，放大倍率约 2.21；这也是后续严格对照需要控制的变量，不能把所有差异直接归于睡眠。

## 判断与边界

高置信：旧进程的播放管线状态与高 CPU 有关，重启同一版本能暂时恢复；本次看到的额外开销集中在系统媒体回调与通知分发，而非旧 PNG 解码路径。

尚未确认：究竟是系统睡眠恢复触发、持续切换片段累积资源，还是两者共同作用。现场没有睡眠前后配对采样，且重启也同时重置了播放位置和展示状态。不能认定已经定位到具体泄漏对象，也不能宣称 CPU 问题已经修复。

## 下一步验证顺序

1. 控制同一片段、同一展示尺寸和相同特效状态，分别记录长时间清醒运行与真实长时间合盖后的 CPU 和调用栈，区分时间累积和睡眠触发。
2. 添加低频生命周期诊断：系统与显示器睡眠/唤醒事件、当前片段、展示阶段、播放时钟和播放器状态。不得逐帧输出日志。
3. 若仅睡眠恢复触发，验证休眠时暂停/解除媒体资源、唤醒时重建播放管线是否足以恢复，覆盖连续和重复通知、未完成 seek 与暂停预览。
4. 若清醒持续切片同样触发，优先做 AVPlayerItem/VideoOutput 生命周期压力实验，确认旧对象释放和通知回调成本是否随切片次数增长。仅重建播放器未必能清除进程级的系统通知状态。
